## Lesson: form WAREHOUSES buffer can bind LOCNAME SELECTs on transfer forms

### Symptom
POST-FIELD fills :$.LOCNAME from stock, then UI shows bin 0 (or destination warehouse default bin).

### Mechanism
1. WARHSNAME POST-FIELD often #INCLUDEs WAREHOUSES/BUF1. BUF1 defaults :$.LOCNAME to 0 when that warehouse has a bin named 0.
2. Filling WARHSNAME and LOCNAME in one SELECT INTO lets BUF1 run after and win.
3. SELECT LOCNAME or MAX(LOCNAME) INTO a stack var from a join that includes WAREHOUSES can bind the **form WAREHOUSES buffer** (already on the default/To warehouse), not the stock join row. Qualifying as WAREHOUSES.LOCNAME can do the same.
4. Hard-coded :$.LOCNAME = ''bin'' in the same POST can stick. Assigning WARHSNAME or WARHS afterward (including from CHECK-FIELD after nested POST) can wipe it again.

### Working park pattern
Fill lot/qty/status without assigning WARHSNAME/WARHS, then hard-code From Bin. Form Prep after every FORMCLTRIGTEXT edit. Still need a non-buffer dynamic path (SQLI or similar).

### Do not
Treat WARHSBAL.LOCNAME as a form-language column (Unresolved identifier on installs where bins live on WAREHOUSES). Rely on CHECK-FIELD alone to beat nested WARHSNAME POST.
